# lib - drasi-lib embedded runtime

Embedded Drasi: sources -> continuous queries -> reactions running fully in-process inside your own Rust application. This crate has its own clippy.toml (stricter than the workspace's), rustfmt.toml, and deny.toml (a separate license/advisory policy).

## Architecture rules (stable conventions; only the runtime-flavor rule has an automated guard)
- Error layering: public API (`DrasiLib`, the `*_ops` extensions, inspection) returns `crate::error::Result`/`DrasiError`; internal modules and plugin traits use `anyhow` with `.context()`; never construct public-API errors with `anyhow!()` - see src/error.rs
- To make a new failure kind pattern-matchable, do NOT add a `DrasiError` variant (the enum is not non_exhaustive, so that breaks the public API); carry a typed error inside `anyhow` and `downcast_ref` at the boundary (existing examples: ComponentNotFoundError in src/managers/, SourceError in src/sources/traits.rs)
- Preserve existing failures with `DrasiError::with_cause`; match `classification()` for public categories and use `downcast_ref()` for typed causes. Never replace a cause or cleanup aggregate with its formatted string. `OperationFailures` retains all causes; `LifecycleReportError` retains per-member outcomes. Their source chains follow only the primary failure, so inspect the aggregate for other causes.
- Modules exported `pub` but `#[doc(hidden)]` in src/lib.rs are NOT private: plugin crates and the host SDK import them in production (e.g. sources::base, bootstrap) - treat their contents as external API despite the hidden docs
- Dependency direction: source/reaction/bootstrap implementations live in components/* and depend on this crate, never the reverse; index backends are injected through the builder and are never runtime dependencies (a rocksdb dev-dependency exists solely to test that injection path)
- End-to-end tests needing components/* crates that depend on drasi-lib (sources/reactions/bootstrappers) go in ../lib-integration-tests - dev-depending on those from lib would create a cycle; index backends do not depend on drasi-lib and may be lib dev-dependencies
- Everything must run on a current_thread tokio runtime - no block_in_place or rt-multi-thread-only APIs (guarded by lib-integration-tests/tests/runtime_flavor_tests.rs)
- ComputationGraph is the only runtime, including with `--no-default-features`; the empty `computation` feature is a transitional build-name alias, not an engine selector. `src/computation/runtime/` hosts ordinary APIs and graph-owned Source/Reaction adapters; `source_manager`, `query_manager`, and `reaction_manager` are facades, never separate registries or executors.
- Component membership, resources, and status come from coherent computation registry publications. `component_graph::ComponentGraph` is a weak, read-only inspection facade; never add a mutable shadow graph or an asynchronous projection/update task. Component events are translated synchronously at the native inspection publication boundary.
- Plugin lifecycle callbacks use the graph-supplied `ComponentUpdateSender`. Its bounded mailbox preserves readiness, first unobserved failure and latest status without polling or a forwarding task; it is not an event history. An ordinary MPSC sender converted into this type retains queue semantics. Restart still requires old workers to be stopped and joined.
- Use `context::workers` for ownership-before-spawn and cancellation-safe joining. Never take/drain handles before awaiting, overwrite unjoined workers, or treat an abort request as completed cleanup. Shared base stops retain handles on timeout/cancellation and surface typed cleanup failures; plugin-specific workers must adopt this too. Status handles may rebind a closed observer after old workers have joined, but cannot replace a live observer.
- `spawn_owned_blocking_worker` acquires the same vacant slot before submitting blocking work, without an extra async bridge worker. Retain the join through actual completion; moving an owned OS-thread handle into an untracked stop-time `spawn_blocking` task is not cancellation-safe.
- `join_owned_worker_gracefully` retains a timed-out worker without aborting it when that worker owns a child-drain boundary, such as an HTTP server. Ordinary `join_owned_worker` still requests abort on timeout. Upgraded connections must also drain before restart; do not detach their send/receive loops or reset shutdown state while old connection owners remain.
- Reactions whose processor must finish submitted effects can use `ReactionBase::stop_common_gracefully`: it preserves ordinary forwarder/queue cleanup ordering but never aborts the processor on timeout. Serialize lifecycle calls and retain a cleanup-required guard through startup and all teardown, including after handles have been joined. This does not persist queued work or upgrade acceptance-only delivery.
- Each DrasiLib owns one ComputationGraph; ordinary queries own internal QueryGraphs with independent scheduling and cleanup. Component batches share the instance namespace and never create another runtime owner.
- Node work budgets bound immediately ready work per poll, reset after suspension, and requeue through the node's own waker. Charge each input/continuation once, including its first forward; charge additional forwards separately rather than charging every nested loop for the same work. Do not accumulate periodic yields across I/O waits or defer the whole controller task for a single node's fairness. Preserve ready-source, output-burst, continuation and control progress on both Tokio flavors.
- Query discovery/status uses the graph's declared semantic kind, not its construction factory. Native query read capabilities are captured on graph-owned component slots and weakly referenced by registry publications. Read facades must fence replacement generations and never start another evaluator; live subscriptions require an actual connected query-results outlet.
- Source/Reaction inventory, status, diagnostics and supported lifecycle operations use declared graph roles too. Subscription readers and timer helpers are not extra public Sources. Native configuration comes from immutable captured values or explicit factory recipes; opaque external bindings remain unavailable, not fake plugin objects. Descriptive snapshots may include native components; reconstruction snapshots must retain each component only in its owning representation.
- `management` is optional and configuration persistence is off by default. Durable desired component definitions and idempotency receipts commit before construction/lifecycle effects. Managed members reject configuration mutations outside `apply_desired_state`; failed definitions remain persisted and inspectable. Unmanaged members and instance-provided resources are preserved during managed reconciliation. Core accepts registered factories and external store/resource-resolver traits, never depends on plugin loading, redb or encryption implementations. Desired configuration is separate from processing state; await shutdown before releasing store ownership.
- Optional `resource_dependencies` are graph-owned lifecycle edges. Constructors receive only actual declared handles; create prerequisites first and clean up users first. Retain prerequisite owners after failed/cancelled dependent cleanup, reconstruct transitive users on replacement, and preserve dependencies in subset snapshots and inspection. Borrowed users cannot retain graph-owned prerequisites. Do not replace this lifecycle with a host cache or infer transaction identity from matching names/paths.
- Persistent management resolvers protect recovery domains before acceptance. Verified shared-domain retirement requires completed stop, initialized output evidence, required journal cursors and scheduled-work checks under actual storage gates, plus graph restart/configuration exclusion through authoritative acceptance. Uncertain commits retain leases; only confirmed rejection resumes old owners. Accepted retirement reconstructs exact old generations and preserves recipes; do not use imperative `RebindResource` (which discards a recipe) for this. Abandoned proof cannot authorize replacement, and unsupported providers never default to empty.
- Native consumer retirement uses the existing DeliveryRunner's validated completion ledger and successfully awaited terminal storage cleanup. It retains no storage or replacement runner. Its held lifecycle blocks reopening, and the graph also freezes the stopped generation; rejection permits reconstruction, while acceptance/abandonment fences the old service. Scope wrappers identify their actual provider dependency, never a matching path. Bootstrap providers need their own held, positively stopped lifecycle; opaque bootstrap interfaces are not automatically eligible. Checkpoint resources must match an actual processing owner's progress publication.
- Explicit loss authorization is revision-bound and persisted with desired configuration and its idempotency receipt. It only permits removal of complete, exactly named recovery domains, including actual live users; it never resets, acknowledges or deletes processing data. It can bypass pending-work checks and a stopped component's prior processing failure, not failed cleanup, missing actual owners or unhealthy transaction gates. Uncertain acceptance retains the same retirement leases. Carrying an accepted authorization forward grants no new permission.
- Native `ComputationComponent::configuration()` is captured at construction/reconfiguration boundaries. Configuration must not change during data processing. Privileged graph/instance configuration snapshots read immutable publications without interrupting component work; missing getters remain explicit `Unavailable` entries. Provider recipes belong to desired topology and stale recipes are discarded on rebind, not inferred from opaque handles.
- Opt-in recovery assertions inspect actual constructed contracts and storage, including ordinary subscriptions. Unknown evidence cannot satisfy a stronger guarantee. Recovery contracts are captured at construction, activation and reconfiguration, never per envelope; activation cannot change an asserted contract. Source progress across stateless intermediates requires the actual atomic owner's resource, not matching names. Assertions do not themselves enable recovery services.
- A query's inbound priority-queue enqueue strategy is chosen by the SOURCE's dispatch_mode, not the query's (Channel = blocking backpressure, Broadcast = drop on full; src/computation/v1/ranked_pipe.rs); the query's own dispatch_mode only governs outbound result dispatch to reactions
- Ordinary source recovery supports framework-sequence checkpoints without source-position bytes. A graph-wide bootstrap-complete marker is not a per-source checkpoint: absent checkpoints must still permit the configured bootstrap, and cursorless bootstrap results must not invent sequence-zero checkpoints. Replay-only starts must not mark a completed bootstrap incomplete.
- Coordinated native bootstrap providers use the borrowed `BootstrapState` service for bounded initialization ownership metadata in the query's actual transaction domain. Persist intent before external initialization, preserve it through explicit query reset, and commit `completion_state` with source watermarks and the completed marker. Partial snapshots remain incomplete; query deprovisioning clears the metadata. Never treat row-wise snapshot loading as one upstream source transaction or add this service's writes to ordinary fast paths.
- Query-scoped bootstrap providers cancel work when their stream is dropped and implement `stop` for owned asynchronous cleanup. Query stop/deprovision awaits that hook before releasing storage or deleting state; retain workers and reject replacement on cancelled/timed-out cleanup. The default hook adds no work for providers without owned workers.
- Scheduled notifications are identified by their control/envelope kind and have a separate rank and deduplication path, never by reserving a source name. A real source named `__future_queue__` must remain valid and its data checkpoints must not suppress scheduled notifications.
- Query, source and reaction queues merge available producer heads without moving a later logical sequence ahead of that producer's earlier admitted work. Timestamp ordering must not invalidate a recovery checkpoint.
- QoS multicast is one append to a shared channel with separate subscriber cursors. Disconnect is not retirement. Only an explicit member-definition change or `retire` releases that member's obligation; lossless capacity exhaustion backpressures.
- Opt-in `DeliveryRunner` records exact input identity/content before destination work and advances only the completed operation prefix. Failed handling, cancellation and uncertain progress writes cannot skip later operations. Reuse the shared output-identity canonicalization; keys include consumer scope/port and producer logical sequence/ordinal, never retry transport identity or replacement configuration. Keep the upstream envelope until the entire batch completes. A handler must provide actual completion; local progress does not make external effects atomic or upgrade acceptance-only plugins. Ordinary sinks must not acquire this runner's work.
- Transactional delivery uses `new_transactional`/`deliver_transactional` and the existing borrowed `TransactionContext`. Business state and one operation's completion commit together in the same actual transaction; no external effects, nested transactions, independent writers or commit-sensitive handler fields. Retry only after confirmed rollback; cancellation and commit/rollback uncertainty fence the owner. Persist and validate handling mode, preserving the original external record shape; never reinterpret one mode's progress as the other. This is per-operation atomicity, not whole-source-transaction visibility.
- `DeliveryBatchIdentity` binds remote confirmation to actual content and configured consumer scope. Derive and compare it before remote effects; never trust a caller's digest or accept queued HTTP 202 as completion. Batch transport must not serialize the full envelope once per operation. Bounded endpoint admission and shutdown cancellation remain the transport owner's responsibility.
- Opt-in `SharedStorageGroup` supplies one built-in producer and its QoS journals from one proven Core transaction group. Declare its IndexBackend resource independently of the producer and name it in every participating pipe's `shared_storage` dependency. Reserve capacity before processing; acquire the storage gate before journal state, including reconstruction. Subscriber progress/retirement leases block rebinding until commit or rollback cleanup. Publish committed cache changes under the shared gate, and wake capacity/publisher/receiver waiters on group failure. Quiesced producer stop leaves journal acknowledgements available; interrupted active storage fences the whole group. Ordinary pipes/producers must not acquire this machinery.
- Optional QoS producer admission uses the same journal/transaction for input and bounded retry receipts. Preserve persistent session epochs and consecutive client sequences; changed or expired retries must never become new input. Validate actual failure survival and keep logical acceptance separate from replay transport sequence. The Rust service alone does not upgrade plugin/network acknowledgements.
- Optional QoS output replay receipts preserve the immediate persistent producer's identity; they do not assign a source identity or coexist with client admission. Only transport ID/sequence and immediate-query post-commit timings are excluded from retry comparison. Preserve inherited context, fail on expired/conflicting identities, and never infer graph-wide branch completion from a channel receipt.
- Replay-enabled QoS journals have persistent UUIDs; configure replay before any event or pipe binding. Built-in durable producers persist bounded destination membership with a matching fingerprint in existing progress, using their existing transaction owner. While output is pending, do not change ports, component/subscriber identities or journal UUIDs; a destination's replacement configuration may change under the same component ID. Recheck after quiescence, reschedule retained output on resume, and reject damaged membership, disabled tracking or automatic query reset rather than discard obligations. This service is not yet exposed through plugin SDKs.
- Sources exposing `SourceAdmission` delegate publication and producer metadata requests to the graph's bounded mailbox, not `next` or another worker. All outputs must use that actual QoS channel; validate scope/identity, schema and sequence before the single commit. Stop revokes queued requests; interrupted writes fence the channel until cleanup/reconstruction. Derive recovery evidence from the bound service and reject weakened live bindings, rather than trusting a component-supplied declaration.
- Graph query factories construct `TransactionTransformer` query bodies using the shared evaluator and core transaction owner. Input/state/output commit together; delivery confirmation is separate, and unconfirmed query output replays without recomputation. Result sequence and replay transport sequence are different identities.
- Default inline-memory query providers are selected in the shared pipeline builder for both ordinary and native queries. Use direct native memory indexes and no-op session control, not plugin-I/O wrappers; preserve explicit/custom/archive provider selection and its cleanup contract.
- Keep large opt-in admission, transaction and durable-completion futures boxed only on enabled branches, including deadline wrappers. Otherwise their async state machines enlarge fast-node state or each ordinary query input's allocation even when recovery is disabled. Use the release `fast_path` and native Host examples with the interleaved comparison runner to measure changes; compare dependency features as well as versions, and retain the original baseline when using diagnostic controls.

## Plugin FFI compatibility surfaces (changes here are wire-format changes: update plugin-sdk/host-sdk marshaling and bump FFI_SDK_VERSION per components/AGENTS.md)
- BootstrapProvider calls cross the FFI boundary through a fixed-arity vtable: subscription settings and BootstrapContext properties are serialized in both directions. Preserve optional resume sequence zero and opaque source positions; errors must not become empty snapshots. Sequence counters remain provider-local across FFI.
- src/channels event types are the wire format: QueryResult crosses the cdylib boundary serialized as-is (its serde shape IS the schema - changes compile clean but break independently built plugins); SourceEventWrapper/BootstrapEvent cross via mirror payload structs in components/plugin-sdk/src/ffi/payload.rs
- SourceSubscriptionSettings (src/config/schema.rs) crosses as individual per-field arguments through the subscribe path
