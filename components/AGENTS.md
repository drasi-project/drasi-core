# components - plugin ecosystem

All Drasi plugins (sources, bootstrappers, reactions, indexes, identity, secret stores, state stores, WALs) plus the FFI backbone (ffi-primitives, plugin-sdk, host-sdk). Plugins build both statically linked and as dynamically loaded cdylibs that external hosts load via FFI. Read components/plugin-architecture.md before touching the FFI layer.

## The plugin contract (discovery is convention-driven)
- Existing ABI plugins follow drasi-{source|reaction|bootstrap|identity|secret-store}-<kind>. Native graph plugins declare `[package.metadata.drasi-plugin]` with `abi-family = "computation"`, an explicit `abi-version`, and `kind`. Both declare `dynamic-plugin` and crate-type ["lib","cdylib"]. Verify discovery with `cargo run -p xtask -- list-plugins`; native metadata is validated rather than inferred from the old category list.
- `export_plugin!` must stay gated behind the `dynamic-plugin` feature (prevents duplicate FFI symbols in static builds)
- The Source/Reaction plugin ABI is versioned by `FFI_SDK_VERSION` (plugin-sdk/src/ffi/metadata.rs); bump it when changing that family's layouts or wire formats. Its current ABI is 0.19; older layouts and identity payloads are rejected. Each family's export macro embeds a binary ABI marker (`drasi-plugin-ffi-abi=` / `drasi-computation-plugin-abi=`); xtask publication and host registry resolution/download use the declared `abi-family` + marker ABI and never infer an ABI from package versions. State/WAL addresses carry typed component ownership and separate storage scope; ABI compatibility never implies recovery support. Native ComputationGraph plugins use the independently versioned computation-plugin-abi 0.2.0 contract: six required lifecycle hooks (Initialize, Start, Pause, Resume, Stop, Dispose with a reason and state intent), a required pure factory describer, and optional, separate management (assess/apply). While the native ABI major is 0, a host accepts only its own major and minor; from 1.0 it accepts the same major with an older or equal minor. Changes to a shared layout require updating every affected ABI family; adding a native-only interface must not change the ordinary contract.
- Event payloads cross the FFI boundary only as serialized MessagePack - never as repr(Rust) pointers
- ffi-primitives must stay dependency-free (std only)
- Indexes, state stores, and WALs are NOT dynamic plugins - they link statically (wiring rules: see lib/AGENTS.md)
- Native libraries are process-pinned and expose only implemented ABI capabilities. Never pass Rust futures, trait objects, Arc/Bytes ownership or borrowed TransactionContext pointers across the new boundary. Transaction participants use the revocable host mailbox and have no commit operation.
- Native plugin producers implement the SDK's `NativeComponent`, `NativeSource`, `NativeTransformer`, `NativeSink`, `NativeService` and bootstrap (`QuiescentBootstrapProvider` or `DurableBootstrapProvider`, every hook required) interfaces. Bootstrap factories implement the required pure `BootstrapFactory::describe` (completion, pairing protocol, element namespace, identity); a provider's served source and the query's labels come from graph relations, never configuration keys, and paired providers are opened by their source's coordinator (computation-plugins/bootstrappers/NATIVE-BOOTSTRAP-PROVIDER-GUIDE.md). Import messages/codecs from computation-contracts and values from core-types; never import graph/query/storage owners merely for plugin data or callbacks. Every capability is declared once in factory metadata: Host services in `Capabilities::services` (`HostServices`), bound in any declared combination and delivered together to the single `Factory::create(request, control, ServiceBindings)` (ABI `FactoryVTable::create` with `ServiceBindingsV1`); only contradictory declarations are refused, by `PluginDefinition::new`/load, which also refuses a declared capability whose implementation (`update_planner`, `activation_credentials`, `bootstrap_coordination`) is missing and an undescribed configuration field (`configuration_details` and `NativeComponent::configuration` are required). Capability hooks live in typed handlers present exactly when declared (`NativeDurableOutput`, `NativeBootstrapInput`/`NativeDurableBootstrapInput`, `NativeInputBindings`), never in silent defaults.
- Compatibility is declared, never inferred or discovered at delivery. Every native factory implements the required pure `Factory::describe(&DescribeRequest)` (ABI `FactoryVTable::describe`): from its own configuration, descriptor and the declared capabilities of bound resources (`admission`, `processing`, ...) it returns the instance's `ComponentDescription` — output identity/replay, input `InputDelivery`, dependency requirements. The Host forwards the answer unchanged and never interprets plugin configuration; consumers must declare keyed inputs. The graph checks edges and resource bindings against it and records mismatches on the nodes (see lib/AGENTS.md). A consumer that offers `atLeastOnce` reads its own `deliveryGuarantee`. The Host selects the delivery mode only from the consumer's declared input guarantee, never per envelope: exactly-once uses the `DeliveryRunner` ledger and an envelope without a durable identity is a permanent typed failure; at-least-once uses no ledger, keeping a durable producer's identity or deriving `Candidate::new_volatile` (an epoch on `DeliveryPosition` v2); destination cursors treat a different epoch as a fresh cursor and never match exactly-once rows to at-least-once items. Sinks classify failed deliveries with `DeliveryFailure` (transient, permanent, or skipped when a `DeliveryRunner`-backed external consumer declaring `skip` has recorded the skip with its own progress) and declare `onPermanentFailure`; the graph owns retries (see computation-plugins/sinks/NATIVE-SINK-GUIDE.md). The stored-procedure sinks share one destination-cursor protocol (`computation-plugins/common/storedproc`); each database implements only its `Session`. Every templating native sink renders through the one engine in `computation-plugins/common/template` (strict, unescaped, fixed helper set, parameter-only SQL mode). Plugins log through the `log` facade; loaded libraries receive the Host's logger through the native logging extension.
- Native transformers follow computation-plugins/transformers/NATIVE-TRANSFORMER-GUIDE.md. The middleware and view transformers share one pipeline, configuration and constant declared kind list (`computation-plugins/common/middleware`); supported middleware kinds are published as a schema constraint on `middleware[].kind` (the query transformer publishes its registry's kinds the same way) and checked at binding, never discovered at construction.
- Select optional consumer wrappers before exporting an operation future, so ordinary native operations do not retain consumer state or gain an extra boxed future. Rebuild the actual cdylib when qualifying Host changes; path dependencies alone do not update it.
- .tsp files inside plugin src/ directories are wire-format documentation, not codegen inputs - there is no codegen step to find, and they should not be deleted

## Writing or changing a plugin
- The README.md files in sources/ and reactions/ are normative RFC-2119 developer guides - read the relevant one before writing or changing a plugin (bootstrappers/README.md is a non-normative how-to); reactions/README.md section 14 is a conformance checklist to walk before finishing
- Reaction traps: `properties()` must return ALL config including secrets (it is the persistence hook - filtering corrupts saved config); the default `enqueue_query_result` silently drops results unless delegated to ReactionBase
- A system's source and bootstrapper must share element-ID generation and type mapping through its <system>-common crate - divergence silently corrupts query state
- reactions/snapshot-test is a publish=false FFI test harness, deliberately exempt from guide compliance
- Test choreography (Docker/testcontainers, host-sdk plugin builds) is owned by the root AGENTS.md "Done means" section
